## 1. 背景与交付终点

测试人员验收某套配置后，维护人员可能继续通过页面、导入、迁移或资源恢复修改它，导致上线前看到的内容与验收内容不一致。

本功能以 `environment_key + pipeline_key` 为冻结范围，提供锁定、解锁、状态和历史记录。冻结期间配置、渠道属性及对应资源不允许通过应用写入口改变，读取和导出继续可用。授权管理员可填写原因解除冻结，后续再次锁定形成新记录。

这是全栈功能：前端操作和提示、IDL/API、后端业务校验、数据库状态与并发协调、管理凭据验证、审计记录，以及本机真实页面与 HTTP 验收。

终点：实现上述能力并通过本 PRD 回归；交付说明记录限制、兼容变化和实际验证范围。不包含按版本读取、不可变快照、发布审批、回滚、个人账号体系、GitHub 分支 Ruleset 配置或生产部署。

冻结不是资源备份，也不能保证外部 HTTP 图片、数据库管理员或直接修改磁盘的行为不变。本版明确保证应用管理的本地／对象存储资源受应用写入口保护；外部 URL 在界面标为“外部内容不受冻结控制”。

## 3. 产品规则

### 3.1 状态与操作

只有 `unlocked` 与 `locked` 两种状态。初始 unlocked，旧环境／渠道升级后默认 unlocked，不自动冻结。

锁定和解锁均填写 trim 后 1—500 字符原因，由服务端记录可信 actor、UTC 时间、状态前后值和递增 revision。reason 是说明，不是身份凭证。状态和操作审计必须在同一个数据库事务提交，审计写失败则状态不变。

锁版无自动过期。页面刷新、服务重启、Redis 关闭、管理令牌轮换或暂时缺失，都不能使 locked 自动变为 unlocked。

请求携带 expected_revision，服务端执行比较与更新。过期 revision 或请求的目标状态已经是当前状态时返回冲突及最新状态，不追加虚假状态变化记录。客户端收到超时先重新读状态／历史，不盲目重试。

### 3.2 允许与拒绝矩阵

| 操作 | locked 范围的行为 |
| --- | --- |
| 列表、详情、runtime、图片下载、预览、导出 | 允许；既有权限和资源错误语义保持 |
| 配置新增／更新／删除 | 拒绝；包括修改 name、description 等元数据 |
| 上传资源到该范围 | 拒绝，不能先创建目录／文件后才报冻结 |
| 归档导入、选择导入、JSON 导入 | 任何实际目标受冻结则整请求在写前拒绝，包括 overwrite=false；不把冻结项静默当冲突跳过 |
| 迁移源范围 locked、目标 unlocked | 允许读取源并复制到目标；源数据和资源不变 |
| 迁移目标 locked | 整个迁移请求在复制资源前拒绝，不产生目标文件或部分配置 |
| 更新／删除当前渠道 | 拒绝，避免名称、激活状态或删除导致冻结范围失效 |
| 更新／删除包含 locked 渠道的环境 | 拒绝；其他未冻结渠道的配置仍可修改 |
| 在同环境新建其他渠道 | 允许，不修改已冻结渠道 |
| 覆盖、修复缺失或改写冻结范围现有资源 ID | 拒绝，即便请求来自另一个范围或来自内部归档工具 |
| 初始化时内容迁移 | 跳过 locked 范围并记录，不能绕过冻结修写内容 |
| 解锁 | 只有管理凭据验证通过且原因、revision 合法时允许 |

导入的目标以映射后的环境／渠道为准，还需包含包准备阶段将修改的环境／渠道元数据。预检查不等于最终保证，提交时仍必须在并发保护中复查。

资源已有行和字节完全相同且不写元数据时可以只读复用；任何实际恢复、覆盖或修复都按写入检查。对无法确定归属的旧资源，拒绝冲突写入而不是猜测属于未冻结范围。归档中的锁定状态／审计字段绝不导入覆盖本地控制数据。

### 3.3 锁定前检查

锁定需确认环境和渠道存在，列出本范围受管理资源引用：

- 引用的资源元数据、文件可读取，关联文件 ID 与路径可明确识别。
- 本版拒绝新的跨范围受管理资源引用；已有跨范围／无法定位资源引用需要先处理，锁定请求返回资源问题列表。
- 使用 content 原文及现有无损 JSON 方法解析，不能让锁定检查改写数值、类型或资源路径。
- 本范围无资源的合法配置可以锁；无配置的已存在渠道也可锁。
- 检查发生在并发保护内，资源写入不能在检查后、锁定提交前插入。
- 外部 URL 不下载、不保证内容不变；返回并展示外部引用提示，允许锁定其配置文本。

锁定不另建快照、不为此复制全部资源。缺失资源应先用正常写流程恢复，再重新锁定。

## 4. 可信管理入口：最小可用方案

本项目尚未建立可证明的个人认证链路。第一版采用专用于冻结控制的管理员 Bearer 令牌，不把可伪造的 X-User-Id、请求体 operator 或现有未校验身份当作管理员。

- 服务端只从进程环境 `RAINBOW_FREEZE_ADMIN_TOKEN` 读取，至少 32 字节；缺失或无效时状态／历史查询可用，锁定和解锁返回 503 `FREEZE_ADMIN_NOT_CONFIGURED`，已冻结范围仍然阻止写入。
- 使用 `Authorization: Bearer <token>` 验证锁定／解锁，常量时间比较；错误凭据返回 401，不改变状态。
- actor 固定记录为 `freeze-admin`，准确表达共享管理身份；不冒称定位真实个人。未来可替换为可信个人身份提供者。
- UI 弹窗需要管理员凭据；令牌只存当前操作内存，操作结束清除，不写 localStorage、sessionStorage、URL、配置导出、日志或审计。
- 示例与测试使用独立生成的测试令牌，不提交真实令牌；共享部署走已有 HTTPS 入口，本地回环测试可 HTTP。
- 此令牌只授予冻结／解冻操作，不给普通写接口绕过 locked 的特权。即便携带正确管理员令牌，也必须先通过解锁接口再编辑。
- 其他普通接口的既有鉴权行为不在本任务整体重写；冻结拒绝对所有调用者一致生效。

同源页面使用现有客户端 header 能力传令牌，确保不被上传／下载辅助请求错误继承。不接受 cookie 自动授权冻结操作，本版不引入长期登录会话。

## 5. API 与数据模型

新增 `idl/biz/freeze.proto`，保留已有 API 和字段。使用 hz 生成模型／路由，禁止直接编辑 biz/model/*.pb.go 与生成路由；手写 handler 完成绑定和错误映射。

所有路径均在当前 base_path 下：

| 方法／路径 | 输入 | 输出 |
| --- | --- | --- |
| GET /api/v1/freeze/status | environment_key、pipeline_key 查询参数 | 当前状态及管理功能是否配置可用 |
| POST /api/v1/freeze/lock | 范围、reason、expected_revision；Bearer 凭据 | 提交后的状态 |
| POST /api/v1/freeze/unlock | 同上 | 提交后的状态 |
| GET /api/v1/freeze/history | 范围、limit 默认20最大100、before_event_id 可选 | 按事件ID倒序，items、has_more、next_before_event_id |

锁定请求示例：

```json
{
  "environment_key":"qa_prod",
  "pipeline_key":"main",
  "reason":"上线前配置验收完成",
  "expected_revision":"0"
}
```

status.data 固定字段：environment_key、pipeline_key、state、revision、last_changed_at（RFC3339 UTC，初始空串）、last_changed_by（初始空串）、last_reason（初始空串）、admin_configured。revision／事件ID使用十进制字符串，避免前端数值范围问题。

状态控制表 `config_freeze_state` 按范围唯一，保存状态、revision和最近变化信息；admin_configured由运行配置计算，不写入业务状态表。事件表 `config_freeze_event` 包含事件ID、范围、lock/unlock、前后状态、revision、reason、actor、时间。事件为追加记录，普通导入和父级删除不清除历史。状态 unlocked 的渠道删除重建时，保留原范围 revision 与审计，不复用已发生过的 revision。

新 API 使用真实 HTTP 状态和同值业务 code：200、400 输入错误、401 凭据错误、404 范围不存在、409 状态冲突或冻结写入、503 配置／并发等待不可用、500 内部错误。新增 machine-readable error_type；409 `SCOPE_FROZEN` 包含实际受阻范围及当前 state/revision，不泄露资源绝对磁盘路径。expected_revision 不匹配用 `FREEZE_REVISION_CONFLICT`。

既有写接口遇到冻结统一返回 HTTP 409／code=409、error_type=SCOPE_FROZEN；其他既有错误继续原契约。新字段需在受影响 IDL 中声明，不以动态 map 掩盖未声明协议。现有前端通用错误处理同步解析该错误，展示锁定原因、刷新状态而不是只显示通用 HTTP error。

历史与状态读取遵循当前管理页面读边界，不返回 token、配置内容或服务器路径。本版历史查询没有独立个人权限系统，交付说明此边界。

## 6. 并发与多阶段资源写入

### 6.1 采用数据库统一写入协调

小团队初版优先正确和可验证：新增持久数据库协调行（例如 `config_write_gate` 唯一固定主键），所有业务写入与冻结状态变更，在事务的**第一条协调语句** UPDATE 同一行以取得数据库写协调，再检查冻结、执行写入和提交。

- PostgreSQL／MySQL 依靠同一协调行事务锁；SQLite 通过事务内首个 UPDATE 取得写锁。不能仅使用进程 mutex 或依赖 Redis 临时租期。
- 所有涉及配置／环境／渠道／资源元数据的 DAO 操作必须使用同一个 tx；同一调用链不嵌套另开 l.db 事务。不允许“检查在 tx、实际写用 l.db”。
- 当前 SQLite 可能使用单连接池，事务内调用旧 l.db 会等待自己持有的连接；实现要显式传 tx 或事务作用域 Logic，覆盖 Service→Logic→DAO 的实际调用链。
- 同一个顶层操作只取得一次协调；内部 helpers 复用 tx，不重新拿锁。
- 多范围导入在协调内一次检查所有目标，任一 locked 就不执行任何数据库／资源写入。
- 写入成功提交后才能失效缓存；状态判定不可使用 Redis 缓存。页面状态可缓存展示但不能作为服务端写入依据。
- 每次实际写入都检查，包括内部资源辅助方法、环境／渠道导入方法和路径迁移，不只在 Handler 放拦截。

该方案会串行化不同范围的写入，本版接受此取舍；读取保持可用。后续有测量需要再缩小锁粒度，不在初版引入复杂多范围锁排序。

### 6.2 文件／对象存储操作不能越过锁定成功时刻

现有上传、归档和迁移包含事务之外的资源副作用。禁止配置阶段释放协调后，资源恢复仍在后台进行，而锁版已返回成功。

第一版顶层上传／归档／迁移须将冻结复查、数据库阶段与实际资源阶段纳入同一次协调存续期；可在持有协调事务期间调用有界资源 IO，所有数据库 helper 仍使用 tx。归档原有部分成功协议保留：配置可提交而部分资源失败，但整个操作的数据库提交和协调释放应在资源处理结果确定之后。

- 锁版请求只在旧写操作完成后才能成功；等待超时返回503，不假报 locked。
- 设置本次设计的写操作总期限60秒、协调等待期限10秒；这是新功能取舍，需在交付中说明影响，超时回滚数据库并清理本次新建临时／未引用文件，不删除原有共享资源。
- 不让 MinIO 调用无界拖住数据库事务；传递超时／取消，未真实运行 MinIO则明确未联调。小团队本地 SQLite＋local 为必须实测路线。
- 数据库回滚不自动撤回磁盘／MinIO；失败资源清理应明确记录，已有文件不能误删。进程崩溃可能留下本次未引用文件，作为可定位残留报告，不宣称跨存储原子事务。
- 若当前实现无法在范围内做到有界协调，应报告具体路径与替代方案，不能简化成“资源开始前看一次锁状态”。

恢复已有资源时不允许覆盖原有不同字节；完全相同只读复用。对于元数据所属冻结范围，不允许以其他范围导入为借口恢复缺失文件或修改该资源行。锁定后的外部物理损坏不能自动修复，需先解锁。

### 6.3 启动与升级

初始化基础表／状态表／协调行在 HTTP 开放前完成，已有渠道补初始 unlocked 状态；重复初始化不能重置状态。启动内容迁移同样检查持久冻结状态并跳过 locked 配置，审计记录不被默认种子覆盖。

如果老版本没有实现冻结却直接连接同一数据库，可能绕过规则；运维文档明确禁止冻结上线后旧版进程共用库。本版保证支持版本的应用写入口，不宣称数据库访问控制或不可篡改审计。

## 7. 前端交互

配置页的环境／渠道选择区域显示“可编辑／已冻结”、最近操作时间与原因，并提供“锁版／解除冻结”“操作记录”。

- 锁版弹窗显示目标范围、影响说明、原因与管理令牌；提交前再次确认当前范围，防止用户切换选择后锁错渠道。
- 冻结后配置增删改、对应资源上传与渠道编辑入口禁用，并说明原因；读取、复制、预览与导出仍可用。
- 导入预览可显示受锁目标，不能只靠按钮禁用保证安全；后端409需展示实际目标与原因。
- 迁移可以从 locked 源复制到 unlocked 目标；目标 locked 时阻止启动。
- 页面已打开后被他人锁定，保存收到409后保留用户输入并刷新状态，不能出现“保存成功”或丢失编辑内容。
- 当前请求取消／网络错误后先读取状态确认，不能自行展示解锁成功。
- 凭据没有配置时，界面提示管理员配置服务端功能；隐藏或禁用操作不意味着解除现存冻结。

使用现有 Vue、Pinia、UI 组件和客户端；不引入新前端框架或全局登录系统。

本任务是新增功能且包含必要事务重组，不宣称纯重构完全等价。普通写入新增冻结409、等待503／超时限制属于明确行为变化；未冻结正常链路与原有错误契约应保持。

测试使用本轮独立 SQLite／local、回环端口、真实 Go HTTP 服务与 Chromium，禁止业务接口 mock；Go层可用夹具和确定性阻塞点控制并发。管理员令牌使用临时测试值，不入日志。

运行：受影响文件gofmt、定向Go测试、一次 `go test -tags=dev ./...`、dev构建、前端类型检查与临时目录打包、冻结专项、`script/test-local.ps1 -Suite Full`。第一批／第二批测试代码原有预期保持，新增测试按新契约断言。

SQLite＋local必须真测；MySQL／PG协调与MinIO取消／写入行为按实际环境独立验证。未测组合明确列出，不把SQLite通过冒充三库或生产通过。默认embed制品限制不伪装成新冻结功能成功。
