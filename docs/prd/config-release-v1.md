## 1. 用一个例子讲清目标

“正式环境＋主渠道”的配置验收通过后，先用现有功能锁住，再保存为 `v1.0`。之后管理员可以解锁编辑区，继续修改、测试，再锁住并保存为 `v1.1`。业务应用接入版本读取接口后，可以先使用 `v1.0`，经管理员操作切到 `v1.1`；出现问题时，再切回已有的 `v1.0`。

| 能力 | 管什么 | 本阶段关系 |
| --- | --- | --- |
| 编辑区 | 正在维护的一套配置和原始资源。 | 沿用现有配置、导入、迁移与资源功能。 |
| 锁版 | 暂停编辑区写入，保护测试和验收过程。 | 保留现有实现；只有已冻结的范围才能创建快照。 |
| 版本快照 | 保存验收时的配置、范围名称与引用资源，旧版本不随编辑区变化。 | 本轮新增。 |
| 生效版本 | 告诉接入新接口的业务应用，当前应该读取哪个快照。 | 本轮新增；切回旧版本也是一次有记录的切换。 |

“生成快照”和“切换生效版本”是两个操作。生成 `v1.1` 不会自动替换正在使用的 `v1.0`，也不会自动解除或新增编辑区锁版。

**兼容性决定：现有 `/api/v1/runtime/config` 继续读取编辑区，默认语义不变。业务应用需要一次性改接新的 `/api/v1/runtime/release`，之后才会跟随生效版本切换。** 在页面和接入说明中明确展示这一点，不能宣称旧接口调用方也会自动切换。

## 4. 必须保持的行为与新规则

### 4.1 原锁版继续工作

- 原 lock/unlock/status/history 接口、管理令牌要求、revision、原因和错误语义保持。
- locked 范围的编辑、导入、迁移写入、资源上传和父级修改拦截保持；管理令牌不能绕过普通写入的冻结检查。
- 解锁只影响编辑区。它不改已保存快照，不改变生效版本，也不使快照失效。
- 切换生效版本是新增的发布管理操作，允许编辑区为 locked 或 unlocked；它只改版本指针，不改编辑区内容和冻结状态。未完成新一轮验收的编辑内容不会随切换进入旧快照。
- 创建快照本身不增加冻结事件、不递增冻结 revision；版本创建和切换使用独立审计。

### 4.2 版本号与不可变性

- 版本属于 `environment_key + pipeline_key`。同范围内版本号唯一，不同范围可各有 `v1.0`。
- 版本号为 1—64 个小写 ASCII 字符，正则 `^[a-z0-9][a-z0-9._-]{0,63}$`，保留字 `active/current/latest` 拒绝。先 trim，不自动转小写。列表按创建 ID 倒序，不推测版本号大小。
- 版本创建后，配置、名称、描述、资源字节、发布说明、来源冻结 revision、创建时间与摘要都不可通过应用修改。没有更新、覆盖、删除接口，也不提供“强制覆盖”参数。
- 生效标记由单独指针计算，不写回快照记录。切换生效版本不会修改两个版本的内容。
- 一旦范围有已提交快照，新增环境／渠道删除保护：即使编辑区已解锁，也拒绝删除该渠道或包含它的环境，返回 409 `RELEASE_SCOPE_HAS_VERSIONS`。无快照范围沿用旧删除行为；名称等允许的编辑仍可继续，旧快照展示保存时的名称。

### 4.3 快照复制范围

保存本范围全部有效配置及其引用的受管资源，不复制同范围未被引用的闲置文件。配置包含 resource_key、alias、name、type、content、remark、is_perm、description；环境和渠道名称也一起保存。读取快照不再查活跃配置行、原资源元数据或最新范围名称。

资源按源 file_id 去重，每份快照独立复制一份文件。配置中的受管引用改成内部 `release-asset://<asset_id>` 标记，返回时再变成该快照自己的下载地址；源文件和快照文件不得用硬链接共享。保留查询参数和 fragment 的既有语义，文件名只作为元数据，不作为磁盘定位输入。

引用识别规则：image/file 解析完整资源引用；object/keyvalue 用 `DecodeConfigJSON` 递归处理字符串；richtext 的受管媒体引用按 HTML 属性边界处理。识别已有 `asset://`、无前缀资源路由及当前完整 BasePath 路由。普通 text 等类型的完整受管地址也要映射；非资源文本按原值保留，不做全字符串粗暴替换。拼接文本中无法安全定位的资源引用、跨范围引用、缺少元数据或文件均拒绝整次创建，返回对应配置与资源问题清单；不能忽略后生成残缺版本。完成捕获后检查不能残留会转向编辑区的受管资源地址；输入中的内部保留标记 `release-asset://` 拒绝，不能把用户伪造的标记当已保存资源。

不下载外部网站：image/file 外链、richtext 外部媒体以及无法可靠解析的嵌入资源拒绝创建，提示先改为受管资源。普通文本、业务 JSON 中的 HTTP 地址作为配置字面值保存，列入 `external_references` 提示；保证 URL 字符串不变，不保证第三方内容或服务响应不变。不得把普通 API 地址误当文件下载，也不得声称冻结了外部网站。

数字不能经 float64 或 JavaScript Number 往返。继续使用无损 JSON 解析；资源替换可改变排版和键顺序，不得改变大整数、长小数、指数或其他非资源字段值。

## 5. 数据与存储设计

### 5.1 新增表的职责

命名可按现有风格调整，以下约束不可省略；不使用数据库 JSON 数值转换承载内容，不配置级联删除。

| 建议表 | 主要数据与约束 |
| --- | --- |
| `config_release_version` | id（自增主键、列表游标）、snapshot_id（服务端 UUID，唯一）、范围、version、creation_request_id（唯一）、request_fingerprint、source_freeze_revision、保存时的范围名称、payload（TEXT）、payload_sha256、manifest_sha256、配置/资源数量和字节数、external_references、reason、actor、UTC created_at。唯一索引 `(environment_key,pipeline_key,version)`。只插入完整版本。 |
| `config_release_asset` | snapshot_id、asset_id（服务端 UUID）、source_file_id、原文件名、content_type、实际 size、sha256。唯一 `(snapshot_id,asset_id)` 及 `(snapshot_id,source_file_id)`。存储相对键由服务端 ID 推导，不保存用户绝对路径。 |
| `config_release_head` | 范围唯一、active_snapshot_id（首次为空）、revision（初始 0）、changed_at/by/reason。指针与 revision 同事务更新；新范围或旧范围无行时，读为“未设置生效版本、revision=0”，GET 不建行。 |
| `config_release_event` | event_id（自增主键）、追加式创建／切换事件、范围、request_id、request_fingerprint、snapshot_id、前后生效 ID、前后 head revision、reason、固定管理 actor、UTC 时间。唯一 `(event_type,request_id)`；创建事件不递增 head revision。 |

范围字段与现有冻结表的长度一致；新版本操作对范围键限制为非空、最多 191 个字符，不能为迁移静默截断旧值。revision、自增 ID、游标对外用十进制字符串；总数用整数。游标缺省为首屏，显式空值、非正整数、溢出值拒绝；末页 next 游标为空字符串。payload 摘要基于有序、无部署前缀的内部数据计算，manifest 按 asset_id 排序计算，规则在代码和测试中固定。

### 5.2 独立资源目录与边界

新增可选环境变量 `RAINBOW_RELEASE_DIR`：配置时要求绝对路径，未配置时使用进程工作目录下 `data/release-snapshots`。目录首次创建后解析、校验为确定的绝对根；HTTP 响应和审计不泄露该路径。多进程共用数据库时必须使用同一个快照目录，测试显式配置共享绝对路径；数据库共享而文件不共享不属于受支持部署。

文件结构为 `<root>/<snapshot_id>/assets/<asset_id>.bin`，准备目录为同一根下 `.staging/<snapshot_id>`。路径只由服务端 UUID 拼成；检查最终绝对路径仍在根目录内，拒绝符号链接／重解析点导致越界。普通上传、导入、迁移、资源清理不得写入快照目录，普通导入也不能以携带目录名的方式注册快照。

初版限制：配置最多 5000 条，序列化后的快照配置 payload（包含字段与范围元数据）的 UTF-8 字节最多 64 MiB；去重资源最多 500 份，单份最多 32 MiB，资源字节合计最多 100 MiB。创建前尽量预查，实际序列化和复制时仍按真实字节再次计数，不能只信文件元数据或先无界 `ReadAll`。超限返回 413，不留下可读版本。空配置、无资源的快照允许创建，计数为0。以上为本次的小团队同步处理边界，需在页面说明；初版不删版本，磁盘使用会随版本积累，交付时说明备份目录和容量观察方式。

创建总期限最多 60 秒，取得写协调的等待继续采用现有 10 秒策略。新入口主动设置不长于 60 秒的 context，不能因调用方已有更长期限而延长。不要增加无界重试、后台任务队列或新中间件。SQLite 锁等待实际验证，其他驱动等待策略另报实测结果。

## 6. 创建与切换流程：文件不完整时不能报成功

### 6.1 创建版本（同步）

1. 验证管理凭据、范围键、版本号、原因、request_id、expected_freeze_revision 的请求格式。
2. 进入现有 `withWriteGate`。先处理幂等重放与版本号冲突；对于确需新建的请求，再确认本地源存储受支持、范围存在、状态 locked、冻结 revision 等于调用方看到的值。通过 txLogic 直接读库，不读可能陈旧的 Redis 缓存。已提交结果的幂等确认不依赖当前源存储类型或当前冻结状态。
3. 在同次协调内捕获全部配置、范围名称与资源计划，检查引用和限额，生成快照自己的资源 ID。写操作、解锁与删除必须排队，不能在复制一半时释放协调。
4. 复制到独占准备目录，边复制边统计和计算 SHA-256；关闭并落盘文件，复读校验。全部成功后，将准备目录移动到同根最终 UUID 目录，不覆盖任何已有目录。内存不同时持有全部文件。
5. 在同一个数据库事务中插入版本、资源清单和创建事件。文件可用后才提交数据库；提交成功才返回 200。全程不改编辑区、不解锁、不更新 head。
6. 失败／取消时回滚数据库，并用独立、短期限清理本次目录。清理失败记录可定位的残留；进程崩溃也可能留下没有数据库记录的孤立目录，它不成为可读版本。初版不自动扫描删除目录。

数据库与文件系统没有跨存储事务。提交结果不明确或响应丢失时，不直接删除最终文件：先用新连接确认该 snapshot_id 是否已提交；只在确认无引用后清理自己的目录，确认不了则保留并记录。客户端使用同一 request_id 查询或重试，避免把已提交版本误删。备份和进程崩溃测试必须覆盖这条规则，不声称抵御直接改盘、掉电或底层介质损坏。

资源文件先完成、数据库后提交，因此资源下载必须先查已提交的版本和清单；仅知道一个磁盘 UUID 不能访问未提交目录。普通列表和读取都只查完整版本，不提供“半成品预览”。

### 6.2 管理写入幂等

两个写入口都要求 UUID 格式 `request_id`，页面一次操作生成一次，网络不确定时重试沿用。request_fingerprint 由标准化的范围、目标版本、expected revision 和原因计算，不包含令牌或字段排列顺序，计算方法固定并测试。

- 创建：同 request_id、同范围／版本／来源 revision／原因重放，返回原已提交快照并标记 replayed，不重复复制或追加事件；即使编辑区后来已解锁也可确认原结果。同 ID 携带不同字段返回 409 `RELEASE_REQUEST_CONFLICT`。相同版本、不同 request_id 返回 409 `RELEASE_VERSION_EXISTS`。
- 切换：同 request_id、同请求重放，返回原操作的 applied_revision，并同时返回数据库此刻的 active 状态，不再次执行切换。不能因重试把后来已经切到 v1.2 的指针又改回 v1.1。不同请求内容仍为冲突。
- 每次重放仍验证管理凭据和请求所属范围。中途失败且确认未提交的请求可以按原 request_id 重试。

### 6.3 切换生效版本／切回旧版

验证凭据后进入同一写协调，先处理幂等，检查目标属于请求范围、`expected_active_revision` 匹配且目标与当前不同，再检查版本完整、全部目标资源可读且 SHA-256 一致。head 由 0 开始独立递增；`UPDATE ... WHERE revision=expected`、切换事件和必要的首次 head 行插入同事务提交，审计失败则不切换。

当前版本与目标相同返回 409 `RELEASE_ACTIVE_UNCHANGED`，不追加虚假切换。过期 revision 返回 409 `RELEASE_ACTIVE_REVISION_CONFLICT` 并给出最新版本与 revision。首次设置也必须是显式操作。切回 v1.0 和切到新版本使用相同接口和规则，不复制数据、不把旧版覆盖回编辑区。

如果等待／检查失败，原生效版本保持；业务读取不能自动改读编辑区、最新创建版本或其他版本。对新控制操作不做自动回退重试。

| --- | --- |
| `POST /api/v1/release/create` | JSON：environment_key、pipeline_key、version、expected_freeze_revision、request_id、reason；管理 Bearer 必需。200 返回版本元数据、source_freeze_revision、数量／摘要、external_references、replayed；不生效。 |
| `GET /api/v1/release/list` | query：environment_key、pipeline_key、limit（默认20，上限100）、before_id（缺省首屏）；按创建 ID 倒序，返回 items、has_more、next_before_id，空 items 显式 `[]`；包括独立的 active 状态。 |
| `GET /api/v1/release/detail` | query：范围＋version；返回元数据、快照配置及资源清单；content 为字符串，受管引用渲染成本版本 URL，不输出内部绝对路径；active 状态单列，不改变快照正文。 |
| `GET /api/v1/release/active` | query：范围；没有生效版本仍 200，`active=null, revision="0"`；有则返回 ID、version、revision 和最近切换说明。 |
| `POST /api/v1/release/activate` | JSON：范围、version、expected_active_revision、request_id、reason；管理 Bearer 必需。200 返回 operation（request_id、replayed、applied_revision）和此刻 active（snapshot_id、version、revision）。 |
| `GET /api/v1/release/history` | query：范围、limit（默认20，上限100）、before_event_id；倒序游标，返回 items/has_more/next_before_event_id；记录创建与切换。 |
| `GET /api/v1/runtime/release` | headers：`x-environment`、`x-pipeline` 必需；可选 query `version`。完全没有 version 时读 active；显式空 version 为 400；指定版本时固定读该快照。无 active 或版本不存在为 404，不回退。 |
| `GET /api/v1/release/asset/{snapshot_id}/{asset_id}` | 仅从已提交清单定位本版本文件；先校验长度与完整 SHA-256 再输出字节。成功使用捕获的 Content-Type（为空则 application/octet-stream），文件名进入响应头前转义校验。不存在的记录 404，已有版本资源缺失／不符 503，不能转读原上传目录或原 file_id。 |

配置原文在 detail 中按字符串返回，避免浏览器 Number 转换；版本 runtime 延续原 runtime 的字段形态，data 包含 configs、冻结时的 environment，以及新增 release：`snapshot_id/version/source_freeze_revision/payload_sha256/selection_mode`。active 模式另返回 `active_revision`；固定版本模式不返回 active_revision。空配置列表为 `[]`。列表等只读管理接口沿用当前部署访问控制，新增创建和切换必须使用管理凭据，普通读取不携带该管理令牌。

运行时资源 URL 形如 `${BasePath}/api/v1/release/asset/<snapshot_id>/<asset_id>`，不使用 active 占位地址。一次请求只解析一次 active_snapshot_id，后续配置、名称和 URL 全按该 ID 构建；切换期间旧请求可完整返回旧版本，新请求可返回新版本，不能出现 v1.0 配置配 v1.1 图片。BasePath 在响应时加一次，内部 payload 和摘要不随部署路径改变。已持久化指针指向不存在的版本属于503 `RELEASE_INCOMPLETE`，不能伪装成“从未设置生效版本”。

版本 runtime 查询绕过编辑区缓存，head 每次从数据库读取，本批不新增 Redis 或进程内发布指针缓存。版本配置、管理状态和资源响应使用 `Cache-Control: no-store`，初版不实现 304 协议。runtime 验证 payload 摘要和清单完整性，并检查资源存在、长度；资源下载验证完整 SHA-256 后再发送，不能先 200 输出一半再发现坏文件。相同长度的损坏至少在资源下载和激活校验时检出。

生效边界：切换提交后，随后开始的新读取应得到新版本；已在途的请求、业务本地缓存不会被服务器撤回。业务应用需要定期重读（接入示例可用 30 秒），成功取得完整配置后整体替换本地一套值，不能只合并新字段而留下旧项。固定 `?version=v1.0` 的调用方不跟随切换。请求失败时客户端如何继续使用上次成功值由应用明确选择，服务端不假装切换成功或自动换版。接入说明需指出：响应保留 JSON 数字原文，但 JavaScript 原生 JSON.parse 仍可能损失大整数，相关客户端应使用无损解析；本批不擅自把既有数值响应全部改成字符串。

### 7.1 错误与管理凭据

复用 `RAINBOW_FREEZE_ADMIN_TOKEN` 的现有最少长度、常量时间比较和 Bearer 校验，actor 固定 `freeze-admin`。凭据只用于控制操作，不成为绕过冻结的通行证；前端只在操作期间内存保留，关闭弹窗即清除，不进入 URL、浏览器持久存储、payload、导出、日志或审计。

## 8. 前端流程与提示

在配置页现有冻结面板附近增加“版本发布”入口，进入独立的环境／渠道版本页。页面同时展示“编辑区：可编辑／已冻结”和“生效版本：未设置／v1.0”，不能共用一个状态徽标让用户误解。

- 创建弹窗：显示并固定打开时的范围、冻结 revision；填写版本号、原因和管理令牌；未锁版时说明并引导使用原锁版入口，不代替用户自动上锁。成功提示“版本已保存，尚未切换生效”，显示新条目。
- 列表与详情：版本号、来源冻结 revision、创建时间／说明、配置数、资源数、校验摘要及外部 URL 边界；只读查看。内容原文展示不经 JSON.parse→Number→JSON.stringify 改写。
- 生效弹窗：显示当前版本→目标版本、head revision、原因和管理令牌。可选择旧版本，按钮文案为“切换生效版本”或“切回此版本”。成功后重新获取 active；遇到冲突显示最新状态，保留选择与原因，不自动带新 revision 再提交。
- 网络结果不确定：保留 request_id 与本次表单于当前操作内存，提供“确认结果／重试本次请求”，成功确认后才显示完成；不生成新 request_id 悄悄重做。关闭或刷新后也可从版本／历史查询已提交结果。
- 切换环境或渠道时丢弃旧范围异步响应，不把 A 的状态展示到 B；操作弹窗打开后仍使用原范围或要求关闭重开，不能提交到后来选中的范围。
- 页面清晰提供两种地址：跟随生效版本、固定某版本；说明旧接口仍读编辑区、轮询／缓存会影响应用看到变化的时间。原冻结记录、编辑入口、静态导出功能保留。
