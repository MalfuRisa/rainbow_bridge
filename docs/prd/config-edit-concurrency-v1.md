# 配置编辑冲突保护 PRD

日期：2026-10-22。状态：设计稿，尚未实施。

## 1. 这轮只解决什么问题

甲、乙同时打开同一条配置。甲保存成功后，乙基于旧内容保存，系统目前会继续接受，可能覆盖甲的修改。本轮让第二次保存明确失败，提示刷新核对，并保留乙尚未保存的草稿。

完成后的规则：**打开编辑时拿到哪一版内容，保存时就只能基于那一版提交；内容在此期间被改过，就不能直接覆盖。** 即使先后操作的是同一管理员的两个标签页，也适用。

本轮只增加配置编辑的乐观并发检查，不增加编辑占用锁、自动合并、强制覆盖按钮、协同编辑、配置历史中心或复杂权限。此前讨论的归档限额、读写性能、K8s、备份等补强均不在本轮实施范围。

## 4. 核心方案：每条配置有独立编辑标识

### 4.1 字段定义

配置表 `resource_config` 新增 `edit_revision`，使用服务端生成的标准小写 UUID v4 字符串，数据库列为 `varchar(36)`。管理配置对象同步输出字符串 `edit_revision`。

更新请求新增顶层字符串 `expected_edit_revision`，位于 config 对象之外；客户端把打开编辑时读到的 edit_revision 原样带回。

这里的“revision”是**不透明的编辑标识**，只用于相等比较，不是递增数字，不用来排序，不是密码或会话令牌。生成使用项目已有 UUID 依赖，不引入新组件。

选择 UUID 的原因：若配置被删除后通过导入以同一个 resource_key 重建，数字从 1 重新计数可能让旧页面意外匹配；重新生成 UUID 可让旧页面始终识别为另一版。也不使用精度或时间格式不统一的 updated_at 作条件。

### 4.2 标识何时产生与变化

| 操作 | edit_revision 规则 |
| --- | --- |
| 新建配置 | 服务端生成新的 UUID，不采用请求自报的值 |
| 普通编辑保存成功 | 生成新 UUID，与字段更新在同一条数据库 UPDATE 中写入 |
| 成功保存相同内容 | 也更换 UUID；一次接受的保存使之前的编辑基线失效 |
| 导入/归档/迁移实际覆盖配置 | 目标生成新 UUID，不复制源标识；即使内容相同，只要执行覆盖也更新 |
| overwrite=false 跳过既有项 | 不改标识 |
| 启动迁移确实修改配置内容或范围 | 同一行的业务字段和新标识一起更新；没有实际改动不更新 |
| 冻结、解冻、发布、切换、读取 | 不修改配置编辑标识 |
| 校验失败、冲突、事务回滚 | 不修改标识或配置字段 |

仅元数据回填 edit_revision 不算修改配置业务内容，不改变冻结状态、发布状态、审计或既有快照。

### 4.3 删除与批量覆盖的范围说明

- **普通删除接口本轮不新增 expected_edit_revision**，继续使用现有鉴权与冻结保护；本轮不扩成删除确认防冲突功能。
- 保存期间配置已被删除，保存返回 404；若已以同键重建，旧标识返回 409，不能更新新行。
- 导入/迁移的 overwrite=true 仍表示管理员明确执行覆盖，本轮不给这些批量入口新增逐条前置条件或二次确认。它们覆盖后必须更换标识，确保此前打开的普通编辑页不能再覆盖导入结果。
- 本次保证的是“过期的普通编辑不能静默保存”，不是保证所有业务写入都只能由第一个操作者完成。

## 5. API 合同

### 5.1 管理读取与创建

`GET /api/v1/config/list` 的每个 data.list 项、`GET /api/v1/config/detail` 的 data.config，以及创建/更新成功的 data.config 都应包含非空 edit_revision。

在 `common.ResourceConfig` 新增未使用的 proto 字段号（当前建议 11），声明为 string。作为输出只读字段，请求对象携带该字段不能直接写入数据库，也不能代替顶层 expected_edit_revision。

详情示例，省略号仅表示这里未展示其他现有字段：

```json
{
  "code": 200,
  "msg": "OK",
  "data": {
    "config": {
      "resource_key": "notice-key",
      "environment_key": "prod",
      "pipeline_key": "main",
      "name": "公告",
      "alias": "notice",
      "type": "text",
      "content": "原公告",
      "edit_revision": "11111111-1111-4111-8111-111111111111"
    }
  }
}
```

编辑基线详情应直接从数据库读取并使用 `Cache-Control: no-store`；不从 Redis 恢复已经过期的正文与编辑标识。列表可保留已有缓存策略，但旧缓存缺少或含非法 edit_revision 时应当作未命中，不输出空标识。

### 5.2 普通保存

保留路径、方法、登录会话和 CSRF：

```http
POST /api/v1/config/update
Content-Type: application/json
X-CSRF-Token: <当前会话令牌>

{
  "expected_edit_revision": "11111111-1111-4111-8111-111111111111",
  "config": {
    "resource_key": "notice-key",
    "environment_key": "prod",
    "pipeline_key": "main",
    "name": "公告",
    "alias": "notice",
    "type": "text",
    "content": "我修改后的公告",
    "description": ""
  }
}
```

成功保持 HTTP 200、code=200、data.config，返回这一次实际提交的正文与**新的** edit_revision。相同旧标识的另一次保存不得成功，即使 payload 相同。

输入必须为规范小写 UUID v4，缺失、空值、null、非字符串或格式错误均返回 HTTP 400、code=400、error_type=`CONFIG_EDIT_REVISION_INVALID`。不设置缺省值，不读最新标识补齐，不给旧客户端保留无条件覆盖通道。

### 5.3 冲突与删除

标识不匹配：HTTP 409。

```json
{
  "code": 409,
  "msg": "error",
  "error": "配置已被其他操作修改，请重新加载后核对再保存",
  "error_type": "CONFIG_EDIT_CONFLICT",
  "resource_key": "notice-key"
}
```

冲突响应不返回可被前端自动替换的最新标识，也不附带完整最新正文；通过明确的“重新加载”操作读取详情。这样避免前端刷新标识后把原草稿不经核对再次提交。

合法更新请求定位不到对应环境/渠道/resource_key：HTTP 404、code=404、error_type=`CONFIG_EDIT_TARGET_NOT_FOUND`，提示“配置已不存在，请刷新列表确认”。不得新建缺失项，不自动查找同 alias 或其他范围的配置。

上述 400/409/404 在本更新接口使用真实 HTTP 状态；不顺带统一其他历史 CRUD 的状态码。HTTP 401/403 及冻结的 HTTP 409 SCOPE_FROZEN 保持既有协议。

处理顺序：管理鉴权/CSRF → 请求结构与 expected_edit_revision 校验 → 原有写协调 → 范围冻结检查 → 数据库目标存在性与编辑标识检查 → 原有内容校验/归一化 → 条件更新及返回结果。冻结优先于内容冲突；请求结构本身非法仍先返回 400。

### 5.4 兼容范围

这是 `/config/update` 有意增加的必填前置条件，旧客户端需适配；前后端必须同批切换。详情字段仅新增，不要求接入方理解 UUID 的内部含义。

发布 runtime、版本详情、快照 payload/摘要、版本静态包不得加入这个动态编辑字段；已发布版本完全不变。归档中如因复用模型出现旧 edit_revision，导入必须忽略，不能由备份或客户端重置目标标识。管理后台普通业务字段的空值/更新语义、alias 不可变规则保持现状，本轮不顺带修复可清空字段问题。

## 6. 后端实现要求

### 6.1 持久化与原子条件更新

保留 withWriteGate 与既有事务，不引入 Redis 锁、进程内排他锁或额外分布式协调。数据库操作必须包含完整范围和编辑标识条件，例如：

```sql
UPDATE resource_config
SET content = ?, ..., edit_revision = ?
WHERE environment_key = ?
  AND pipeline_key = ?
  AND resource_key = ?
  AND edit_revision = ?;
```

省略部分代表按当前 DAO 规则更新的业务字段，不表示应改成完全覆盖所有字段。

- 受影响行必须恰好为 1 才成功；0 行在同一写事务内按目标是否存在区分 404/409；大于 1 为内部异常，整体回滚。
- 可以先读当前行决定错误和做业务校验，但不能仅“先比较、再无条件更新”。WHERE 必须带标识，数据库仍是最后防线。
- 取得更新后的行必须在同一事务内完成并保存为本次返回值，提交后只返回该结果；不能提交后通过 Redis/再次查询返回另一次并发操作的正文与标识。
- Service、Logic 的普通编辑入口都必须传递并校验 expected_edit_revision，不能只在 handler 中防护。内部批量覆盖使用命名清楚的独立方法，不能让公开更新因为缺少标识自动走覆盖方法。
- 成功提交后沿用缓存失效；冲突和失败不作“保存成功”副作用。Redis 失效故障不撤销已提交更新，也不能成为条件更新使用缓存值的理由。

### 6.2 存量迁移

新增列允许以空默认值完成兼容建表，随后在 HTTP 接口开放前为 edit_revision 为空的存量行逐条生成 UUID；最终所有有效配置都有非空标识。回填使用“目标行且原值仍为空”的条件，不覆盖并发进程已经生成的值。

回填可以幂等重跑，重启不改变已有标识，不修改配置内容/原始时间/锁版和发布记录。数据库迁移失败应拒绝开放 HTTP，不以临时生成且未落库的 UUID 冒充有效版本。

新增配置和各个覆盖入口必须主动生成标识，不能依赖全表相同的 SQL 默认值。启动默认范围迁移、资源路径归一化中的实际改写同样审查：保持原有冻结/范围规则，用原子字段写入更换标识；只为本需求补齐标识维护，不扩大为启动迁移整体重构。

旧二进制不会维护新标识，本版不承诺新旧二进制混跑安全；升级时一并替换旧写入进程，不能滚动混用后又声称保护有效。

## 7. 必要的前端接入

### 7.1 读取与保存

- `vue/src/lib/api/types.ts`、`lib/types.ts`、`lib/api/transformers.ts` 必须完整传递 edit_revision；API 层不得误删为未知字段。
- 打开编辑时通过详情取得**同一次响应里的正文和标识**，详情成功后再初始化可保存的表单。若失败保留错误状态，不拿列表旧正文配新标识。
- 基线固定在这次编辑会话里；后台列表刷新不能修改表单草稿或它的 expected_edit_revision。
- 配置 API 使用专门的更新请求，顶层携带 expected_edit_revision，保留 config 包装；不要修改通用 BaseApiService 使环境/渠道等其他更新接口被迫带这个字段。
- 配置范围/目标变化时丢弃旧详情的迟到响应，不能让 A 的正文或标识填进 B 的表单。
- 编辑标识不展示在表单中，不增加用户输入步骤。

### 7.2 冲突体验

409 CONFIG_EDIT_CONFLICT 时：不关弹窗、不显示成功、不清空草稿，显示“这条配置已被其他操作更新。你的修改尚未保存，请重新加载后核对。”

提供“复制我的草稿”“重新加载”“取消”三个简单操作；不提供“强制覆盖”或自动合并。

- “复制我的草稿”复制 name、alias、type、content、description 等本次实际可编辑字段的 JSON，content 保持字符串，避免格式化损伤大整数；不复制 Cookie/会话信息，也不将草稿写入 localStorage。
- “重新加载”需明确提示“将用最新配置替换当前未保存内容”，用户确认后才请求详情。请求失败保留原草稿和冲突状态；成功后将正文与标识一起替换，清除冲突，由用户核对后重新编辑保存。
- 冲突状态下禁用重复保存旧基线；用户必须重新加载或取消后重开，不在后台自动获取标识再覆盖。
- 404 CONFIG_EDIT_TARGET_NOT_FOUND 时保留草稿并提供复制、取消/返回列表；重新加载不能重新创建配置。
- 冻结和登录失效继续使用既有处理；不要把任意 409 都当成编辑冲突。

网络超时不一定代表服务端没保存。本轮不新增 request_id 幂等机制：保留草稿并提示“保存结果未确认，请重新加载核对”，不能拿新标识自动再提交；服务端若已成功，重发旧基线只会冲突，不会二次覆盖。这个提示应与已确认的编辑冲突区分。

## 8. 实施顺序

1. 建立独立实施工作区，核对普通编辑及导入/迁移/启动改写入口，先明确请求与响应模型。
2. 加列与幂等回填；补数据库条件更新及冲突测试，再接 Service/handler；统一所有写路径更换标识。
3. 接前端详情基线、请求透传和草稿保留；更新既有测试夹具，使普通修改请求先取目标自己的编辑标识。不得在 HTTP 测试 helper 里遇到 409 自动刷新重试。
4. 运行下列验收，补专业 API 文档；按最小相关范围回归，交付整合后的代码和本 PRD 最终结果。

## 9. 验收场景

| 编号 | 输入或时序 | 必须得到的结果 |
| --- | --- | --- |
| C01 正常保存 | 详情拿 R1，带 R1 更新 | 200；正文已改，返回 R2 且 R2≠R1；数据与标识同次提交 |
